# 项目分析报告

## 1. 评估结论

项目是一个面向单场活动的实时手写签名墙，当前代码已经覆盖参与者提交、大屏展示、管理员审核、现场监控、数据导出和基础部署运维，功能完成度明显超过原型阶段。

本轮迭代将发布目标统一为 `v1.0.0`。在本次工作区改动中已经完成三项发布阻塞修复：

- 管理员 ZIP 导出支持当前主路径的矢量笔迹，并对旧版 PNG/JPEG 数据保留回退处理。
- 大屏几何上报要求近期的大屏会话 Cookie，并限制尺寸、比例和总像素，避免任意客户端污染导出布局或触发超大 Canvas。
- 未配置 `ADMIN_TOKEN` 时服务启动即失败，不再使用内置开发令牌。

当前版本仍应称为“发布准备完成、待最终验收和打标签”，不能把未完成的真实设备彩排、容器构建和线上回滚演练描述为已验证。当前 Git 历史没有 `v1.0.0` 标签，也没有执行提交或推送。

## 2. 系统边界与主要能力

| 子系统 | 已实现能力 | 关键入口 |
| --- | --- | --- |
| 参与者端 | 手写坐标采集、横屏书写、署名必填、提交成功反馈 | `/mobile`、`POST /api/events/{slug}/submissions` |
| 大屏端 | 背景图、二维码、实时签名动画、拥挤度自适应排布、断线重连 | `/display`、`/ws/events/{slug}/display` |
| 管理端 | 活动配置、状态控制、展示数量、二维码缩放、审核、CSV/ZIP 导出 | `/admin`、`/api/admin/...` |
| 现场监控 | 统计、最近提交、PNG/ZIP 下载、删除当前页 | `/monitor`、`/api/monitor/...` |
| 服务端 | FastAPI、SQLite WAL、批量写入、限流、鉴权、健康检查、启动迁移 | `app/main.py` |
| 部署 | Docker Compose、systemd、Caddy/HTTPS 脚本、回滚和基线检查 | `Dockerfile`、`deploy/`、`tools/` |

项目是单体部署模型：一个 Uvicorn 进程同时提供页面、API、WebSocket 和导出服务，SQLite 是唯一持久化存储。这个边界适合单场活动和几百人级突发提交，不应直接按多实例 SaaS 架构宣传。

`app/main.py` 目前约 1300 行，承担了配置、模型、数据库、鉴权、导出和全部路由。作为 v1.0 单体实现可以接受，但后续迭代应优先按“配置/数据库/领域服务/路由”拆分，而不是继续向单文件追加功能。

## 4. 数据与请求流

### 4.1 提交链路

1. 手机端在 Canvas 记录 `strokes`，每笔是若干 `[x, y]` 坐标。
2. 服务端校验署名、笔迹数量、点数、坐标和请求大小；坐标越界会裁剪到边界。
3. 提交进入单进程批量写入协程，SQLite 以 WAL 模式提交。
4. 写入成功后通过 WebSocket 广播 `submission` 消息。
5. 大屏、管理员和监控端分别按各自的权限和状态读取数据。

矢量笔迹是当前主数据格式；`signature_data` 只为旧客户端和旧数据库记录保留。PNG 导出必须从矢量数据重绘，不能假设所有记录都有图片字段。

### 4.2 大屏和导出链路

大屏计算舞台尺寸、二维码占位区域和签名数量，使用 `wallLayout.js` 得到确定性位置，并把几何写入服务端。监控页导出 PNG 时先取回该几何，再用相同布局算法放大重绘，因此导出图可以匹配现场画面。

大屏几何写入不是管理员凭据：它使用 `/display` 返回的短期签名 Cookie，配合同源 Cookie、严格尺寸边界和前端异常值过滤。由于大屏本身是公开页面，这仍然是范围受限的能力令牌，不等价于管理员认证；后续若需要强对抗安全，应改为服务端持有的显示实例注册机制。

## 6. 风险与技术债务

| 优先级 | 风险 | 影响 | 建议 |
| --- | --- | --- | --- |
| P2 | lockfile 由当前验证环境生成，跨平台重新生成流程仍需固定 | 不同 Python/平台升级时需重新解析并验证 | 当前 Docker/CI 使用 runtime/dev lock；依赖升级需通过完整发布门禁 |
| P1 | 写入队列、限流和 WebSocket 连接均为进程内状态 | 多 worker/多实例会丢广播、重复限流或各自排队 | v1.x 保持单进程并明确约束；需要扩容时迁移 Redis/外部队列和 PostgreSQL |
| P1 | 监控令牌具备删除权限 | 值班人员可执行破坏性操作 | 已加入一次性监控码和短期签名会话；v1.1 增加操作审计和更细角色权限 |
| P1 | 备份恢复尚未完成真实演练 | 活动数据丢失后仍可能无法恢复 | 已加入 SQLite 在线备份脚本和完整性检查；发布前完成新目录恢复与回滚演练 |
| P1 | 浏览器验收脚本还没有统一 CI 门禁 | CSS/Canvas/移动端回归可能只在现场发现 | 固定 Chromium 版本，建立 smoke、导出、横屏和 500 条布局 CI job |
| P2 | `app/main.py` 过大，前端是无构建的全局脚本 | 修改边界和依赖关系逐渐变得脆弱 | v1.1 做低风险模块拆分；不为 v1.0 引入大型前端构建迁移 |

## 7. v1.0.0 发布门槛

只有以下项目全部完成，才应创建正式标签：

- [x] 版本元数据统一为 `1.0.0`。
- [x] 管理员 ZIP 能导出矢量和旧图片两类签名。
- [x] 大屏几何写入具备会话边界和资源上限。
- [x] 缺失管理员令牌时不能启动生产服务。
- [x] 本机后端回归测试通过。
- [ ] 容器镜像成功构建并启动，`/health` 返回 200。
- [ ] 真实大屏 + 真实手机完成连续提交、断线重连、导出和活动结束流程。
- [ ] 至少完成一次 SQLite 备份恢复和一次上一版本回滚演练。
- [ ] 固定浏览器版本下完成大屏、监控导出、横屏书写和 500 条布局验收。
- [ ] 审阅 `git diff`、确认无个人数据/密钥，再提交并创建 `v1.0.0` annotated tag。

## 8. 总体判断

从产品能力看，项目已经具备首个正式版本的核心功能；从发布工程看，当前更准确的状态是“可发布候选版本”。建议先完成上面的现场和部署门槛，再把本轮工作区改动作为一个可回滚的发布提交，创建 `v1.0.0` 标签。后续最有价值的投入不是继续堆叠视觉功能，而是迁移可审计、备份恢复、CI 浏览器门禁和凭据治理。
